# Single-file bundle builder (SCS Vessel Watch)

> 'Dark' means only that no AIS position was matched to a radar contact. It does not mean illegal. Many vessels need not carry AIS, AIS can be off for lawful reasons, and satellite and terrestrial AIS both have blind spots. An AIS gap is not proof of intent. Where the live feed heard nothing, a contact is `no_coverage`, never dark. Every page this builder makes carries the product caveat (`app/CONTRACT.md` section 1.1) in its `meta` part and in every record, and the frontend shows it on every view.

`build_single.py` turns the frontend's single-file shell (`app/frontend/dist-single/index.html`: all JavaScript and CSS inlined, no data) plus the real product data into two self-contained pages:

- `app/build/out/scs_vessel_watch_open.html`: open build, no Global Fishing Watch data, commercial-clean as far as the sources allow (live AIS relayed by aisstream.io, terms UNVERIFIED, board D4.7).
- `app/build/out/scs_vessel_watch_research.html`: research build, adds the GFW identity of the September run, noncommercial (CC BY-NC 4.0).

Each page is at most 15,000,000 bytes (contract section 6.3) and makes no network request: every script, style and image is inline, the map has no tiles, and the check proves that the only URLs the page loads are `file:`, `data:` and `blob:`. The outputs are build artefacts: `app/build/out/` is git-ignored, the pages are never committed, and the lead publishes them as private artifacts.

## Usage

```
# both pages (about 3 min each; the first run after a Sentinel-1 pass also reads the new chips from AWS)
make app-single                                   # = the line below with FRONTEND=app/frontend/dist-single/index.html
PYTHONPATH=app/backend nice -n 10 /home/user/.mamba/envs/darkvessel/bin/python app/build/build_single.py \
    --build both --frontend app/frontend/dist-single/index.html
# one build, no chips, or cached chips only
... build_single.py --build open --no-chips
... build_single.py --build research --offline-chips
# evaluate a budget change (the default is the contract 6.3 table)
... build_single.py --build both --budget contacts=6.0 --budget cells=0.75 --out /tmp/x

# checks: both pages at 1280 x 800 and 390 x 844, dark and light, plus the 50-contact spot check and the static scans
make app-check                                    # check_bundle.mjs, then the frontend smoke check on each page
NODE_PATH=/opt/node-tools/node_modules PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers node app/build/check_bundle.mjs app/build/out
```

Options: `--frontend PATH` (the shell; default `app/frontend/dist-single/index.html`, built by `npm run build:single`), `--out DIR` (default `app/build/out`), `--chips-mb N` (lower the chip budget), `--no-chips`, `--offline-chips` (cached chips only), `--no-cache` (rebuild every cached intermediate), `--budget PART=MB` (repeatable; for evaluating a contract change, never for a published page). The script inserts `app/backend` into `sys.path` itself; `PYTHONPATH` is harmless. Never run `playwright install`: the checks use the preinstalled Chromium in `/opt/pw-browsers`.

Outputs per build: the page; `<build>_report.json` (part sizes, budgets, drops, counts, record and chip statistics, content checks, timings); `spotcheck_<build>.json` (50 contacts as `GET /api/v1/contacts/{det_id}` returns them, live matched contacts first, for `check_bundle.mjs`); `check_bundle.json` and `shots/` from the check.

Rebuild after every live pass the watcher processes (the newest pass must be in the page), after a leads rebuild and after `npm run build:single`. Publish only a page whose check passed.

## How it works

1. **Records from the backend.** The builder starts `scs_api.store.Store` for the build (the catalog, loaders and record builders that answer the API) and takes every Contact, Vessel, Light, Lead, Pass and Cell record from it, so a value decoded from the page equals the API value within the column's stated scale. In the open build the catalog registers no path under `data/research/` and its guard refuses one; `tests/app_build/test_bundle_build.py` wraps every file reader (pyarrow, pyogrio, rasterio, geopandas, `open`) and asserts that the open build touches nothing there.
2. **Parts.** One `<script type="application/json" id="scs-part-NAME">` per part before `</body>`, meta first, then contacts, chips, lights, vessels, events, leads, passes, cells, geo, rasters, camau (contract 6.1). The layout is the normative one of contract section 6.4 (the readings 1 to 16 of `app/frontend/README.md`); the frontend's embedded adapter is the reference reader. Every `<` in the JSON is written as `\u003c`, so no data can end the element early.
3. **Encodings** (contract 6.2). Columnar parts hold little-endian typed arrays in base64 with an explicit `na`. Per column the builder takes the narrowest form: `const` when every row holds one value, else the narrowest of u8, u16 or i16, u32 or i32 at the column's scale, or `dict8`/`dict16` over the exact values when that is smaller. Times are `time` (u32 seconds from the column's first UTC midnight); lead times the frontend reads as text may be a `dict` of ISO strings. Ids are `detid` and `lightid`; geometry is `geom` (lon and lat x 10,000). `scs_bundle/encode.py` holds the encoders and a Python decoder that mirrors `app/frontend/src/adapters/columns.ts` line by line; the tests round-trip every encoding through it, and the browser spot check decodes with the frontend's own code.
4. **Identity first (P0).** Rows are ordered live passes (newest first), lead primaries in queue order, matched contacts, the rest of the September run, fixed structures, the Ca Mau scene. Identity strings live once per vessel: `vessel_ref` and `nearest_ref` are `ref16` rows of the `vessels` part; a matched contact whose eight identity fields differ from its vessel row carries its own strings in its record (behaviour rule 6). No drop rule removes a matched contact: rules 4 and 5 touch only unmatched or unchecked September rows, and rule 7 never drops a live pass that holds a matched contact (below).
5. **Records.** A record holds the API fields that are not bulk columns, nulls left out (and `match_ambiguous` only when true, reading 16), and only the provenance entries that differ from the row's `prov_sets` entry (the adapter's `provSetName`). Every page carries, whatever the budget (the build fails otherwise): the full record of every matched live contact, every hand-checked live contact (`review_note`) and every ambiguous live contact (candidate MMSIs), which hold the identification evidence of README reading 16 (azimuth shift, ambiguity, hand-check note, identity label), and the own identity strings of rule 6. Then, while the part budget allows: chip contacts, lead evidence contacts, the other unmatched live contacts (newest pass first). `field_prov` (contract 1.3.0 field-level provenance) is not carried: the page does not read it, the local app serves it. The fields that live only in records are counted for the contacts without a record and listed in `meta.dropped` (for example `s2_item`, `extra.source_caveat`, `extra.himawari_start`, the research build's GFW evidence columns), leaving out what the page holds another way (lead ids of a lead primary, the aisstream identity label, a nearest AIS name equal to its `nearest_ref` vessel row).
6. **Chips.** 130 x 64 px WebP (VV 64 x 64, 2 px gap, VH 64 x 64, 10 m pixels, 2nd percentile to maximum per polarisation, quality 70), read remotely from the AWS mirror with the CNN verifier's helpers (`darkvessel.ml.regional_verify.tile_groups`, `darkvessel.ml.chips.chips_db`, `darkvessel.live.scene.LiveGRDScene`) and cached as `data/cache/chips/<det_id>.webp` (git-ignored; the local app serves the same files). Selection order: tier 1 primary contacts of leads by priority; tier 2 matched live contacts; tier 3 CNN-accepted unmatched live contacts; tier 4 the label queue sample. The part fills until the next chip would pass its byte budget. A failed read is skipped, counted, and noted in `data/cache/chips/failed.json`.
7. **Budget and drops** (contract 6.3). Every part is measured as the bytes of its element. A part over its budget applies its own rules: contacts rule 4 (open) or 5 (research), then rule 7; vessels rule 6; lights rule 2; camau rule 3; leads keep the highest-priority rows. Extension columns (contacts, vessels, lights) are added in a fixed priority order only while the part stays within its budget. Then the page total: rules 1 to 7 in order until the page is at most 15,000,000 bytes; a part still over its budget, or a page still over the cap, fails the build. **Rule 7 in this builder never drops a live pass with a matched contact** (the contract puts such a pass last; the owner's P0 rule keeps it): if nothing else can go, the build fails. Every drop, every column or field left out and the count of records left out is listed in `meta.dropped`, with the number of contacts for rules 4, 5 and 7.
8. **Content checks** (the build fails on any): open build: no field name containing `gfw`, no "Global Fishing Watch" and no `gfw_` in any data part, no `research_only` true (plain, const or bool8 rows), no EEZ polygons (only the published boundary lines); both builds: no 12-character prefix of any `.env` value anywhere in the page, no name of the toolkit's copyright holder in a data part (read at run time from `@blueprintjs/core/package.json`, spec PW-16). The `.env` file is read only to take those prefixes into memory; no value is printed, logged or written (a hit names the variable only). Em and en dashes in the data are counted.
9. **Object context** (board D5.3, README reading 13; `scs_bundle/parts.py` `context_block`, `bundle.py` `fit_context`). Contacts and lights carry a part-level columnar `object_context` block, rows parallel to the part's rows, built from the same table rows and the same rounding, time and source rules as the API (`ContextData.records`): `time_utc` (null where `data/ocean_context_objects.parquet` has no row, so the page says "no ocean context" only where that is true), `region`, `cell_id`, one column per field (presence as bool8, board D4.3) and the valid-time and dataset columns each field names (`time_col`, `src_col`). Page scales: depth 0.1 m, distance to the coast 0.01 km, distance to a port and to a front 0.1 km, SST 0.001 degC, SST gradient 0.001 degC/km, chlorophyll 0.001, current 0.01 m/s, mixed layer and waves 0.01 m. Records never repeat it. Its bytes are not in the contract 6.3 budgets (contract 6.4, open item 8.19): after every other part fits, the blocks fill the room left under the cap (less a 20,000-byte margin). Every row with context keeps `time_utc` and `region`; fields then join in a fixed order (depth, distance to the coast, shipping presence all and fishing, SST, waves, distance to a port, chlorophyll, cell, distance to a front, current, the other presence types, SST gradient, mixed layer) while both blocks fit. The fields left out are listed in `meta.dropped` with the rows that have context, and the block's caveat ends with "This page carries N of the 16 context fields to stay within its size cap; the local app shows all of them", which the Context section shows. The context never makes another part drop.
10. **Cache.** Expensive intermediates (API records, geo, rasters, Ca Mau backdrop, cell records, pixel positions) are gzipped pickles under `data/cache/bundle/` (git-ignored under `data/cache/`), keyed by the builder version, a hash of the builder's and the backend's Python sources and the modification times of the input files. The record frames depend on every catalog file of the build (live review tables, weather sidecars, object context, leads, ...), except the recorder's growing position and static folders for contacts and the chip cache.
